PURPOSE
-------
Clanker is Kyle's primary always-on Ubuntu VPS. It acts as a mixed application
host, protocol server, VPN/router, observability node, Yggdrasil overlay node,
DN42 edge router, reverse-proxy host, authoritative DNS host, recursive/caching
resolver, and backup/storage node.

The DN42 design is now a real multi-router / multi-edge network:

    Clanker
        edge/router #1
        primary authoritative DNS (ns1)
        three direct external DN42 eBGP peers

    ScopeCreep
        edge/router #2
        secondary authoritative DNS (ns2)
        connected to Clanker by a dedicated WireGuard core and iBGP
        has its own external DN42 connectivity

Clanker and ScopeCreep exchange DN42 routing information over iBGP. Clanker
can therefore select routes learned either directly from its own external peers
or indirectly through ScopeCreep.

This file is intended to answer:

- What is Clanker?
- What runs here?
- What starts it?
- Where is its configuration?
- Where is persistent data?
- Which identities matter for recovery?
- What networks does it participate in?
- What backup responsibilities does it have?
- What would be needed to rebuild it?
- What remains worth documenting or cleaning up?

It is deliberately broader than a backup manifest.

    A working WireGuard handshake does not prove BGP is established.

    packet path separately.

ROUTING POLICY
-------------------------------------------------------------------------------

Clanker's external eBGP export remains intentionally restricted to the
registered aggregate prefixes:

    172.20.220.48/28
    fdf0:e12c:5528::/48

Internal host routes such as:

    172.20.220.51/32
    172.20.220.52/32
    172.20.220.59/32
    172.20.220.60/32
    172.20.220.61/32
    172.20.220.62/32

and their /128 IPv6 equivalents are not intended to be advertised externally
as more-specific routes.

The aggregate represents the entire AS externally.

Third-party routes can be exchanged internally between Clanker and ScopeCreep
for path selection.

General transit advertisement between unrelated external peers is NOT
intentionally enabled.

Enabling full DN42 transit remains a deliberate future policy decision and
should not be achieved accidentally by loosening export filters.
