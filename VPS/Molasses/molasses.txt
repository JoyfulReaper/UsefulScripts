MOLASSES
========
Infrastructure / Recovery / Service Overview
Snapshot date: 2026-09-24

PURPOSE
-------
Molasses is Kyle's always-on home Debian server. It currently acts as a local
network utility host, DNS resolver/filter, Docker application host, monitoring
host, IRC/web utility host, and Matrix homeserver.

This file is intended to answer:
- What is Molasses?
- What runs here?
- What starts it?
- Where is its configuration?
- Where is persistent data?
- Which secrets and identities are irreplaceable?
- What should actually be backed up?
- What is intentionally NOT backed up?
- What would be needed to rebuild it after a drive failure?

It is deliberately broader than a backup manifest.

The backup policy is intentionally conservative. In particular, Matrix is NOT
being treated as a full-state archival service. The goal for Matrix is to retain
the absolute minimum required to rebuild the same homeserver identity and
configuration after a disk failure, not to preserve the PostgreSQL database,
room/event history, or media store.

8. MATRIX MINIMAL DISASTER-RECOVERY POLICY
===============================================================================

Matrix is intentionally NOT receiving a full backup.

The recovery goal is:

    "After the Molasses drive dies, rebuild a fresh Synapse instance that uses
     the same kgivler.com server identity and configuration."

The recovery goal is NOT:

    "Restore every user, room membership, event, message, token, database row,
     thumbnail, upload, or cached remote media exactly as it existed."

Therefore the Matrix backup includes only the small identity/configuration set:

    /opt/stacks/matrix/compose.yaml
    /opt/stacks/matrix/.env
    /opt/stacks/matrix/synapse/homeserver.yaml
    /opt/stacks/matrix/synapse/kgivler.com.log.config
    /opt/stacks/matrix/synapse/kgivler.com.signing.key
    /opt/stacks/matrix/synapse/registration_shared_secret

Also preserve the external configuration required to make the homeserver
reachable again:

    - Cloudflare tunnel configuration/credentials for matrix.kgivler.com
    - kgivler.com .well-known Matrix delegation configuration, where that
      configuration is actually hosted

EXPLICITLY NOT BACKED UP FOR MATRIX:

    /opt/stacks/matrix/postgres/
    PostgreSQL logical dumps
    /opt/stacks/matrix/synapse/media_store/
    thumbnails
    remote media cache
    local uploaded media
    Matrix message/event history
    room state/history
    access-token/session state
    user/account database state

Consequences of this policy:
    - the same Matrix server name and signing identity can be restored
    - the Synapse deployment/configuration can be recreated
    - the existing database-backed Matrix state is intentionally disposable
    - local accounts and server-side room/membership/history state are NOT
      recoverable from backup
    - users/services may need to be recreated or rejoined after a catastrophic
      disk loss

This is an intentional "identity/configuration recovery" policy, not a complete
Matrix service restore.

If that policy changes later, the PostgreSQL database can be added as a separate
offsite backup without changing the tiny P0 identity backup.

17. BACKUP ARCHITECTURE / POLICY
===============================================================================

Molasses backup design is intentionally split by data value rather than by
directory size alone.

A. TINY IRREPLACEABLE / IDENTITY / ACCESS MATERIAL

    Examples:
        Matrix signing key
        Matrix .env / registration shared secret / homeserver config
        WireGuard private configuration
        important SSH/access material
        Cloudflare credentials/configuration needed for recovery
        backup repository credentials (stored separately/out-of-band as needed)

    Policy:
        - preserve automatically
        - encrypted peer copy on a VPS where practical
        - independent encrypted offsite object-storage copy

    Rationale:
        These files are tiny, critical, and have negligible storage impact.

B. SMALL USEFUL APPLICATION STATE

    Examples:
        Uptime Kuma
        selected NetAlertX state
        selected Scrutiny state
        selected Pi-hole configuration
        Dockge/The Lounge state
        custom systemd units and service configuration

    Policy:
        Back up where worthwhile.
        Prefer object storage plus peer copy when size is tiny.
        Do not preserve large history/cache data just because it exists.

C. MATRIX BULK / DATABASE STATE

    Current examples:
        PostgreSQL database: ~2.7 GB
        Synapse media store: ~601 MB

    Policy:
        DO NOT BACK UP under the current minimal Matrix recovery policy.

    Reason:
        The goal is to recover the homeserver identity/configuration, not to
        archive Matrix state.

D. REPRODUCIBLE CONFIGURATION

    Examples:
        compose.yaml files
        selected systemd units/timers
        Unbound configuration
        non-secret service configuration
        public infrastructure documentation

    Policy:
        Keep in Git where appropriate.
        Small configuration may also be included in encrypted backups.

E. REGENERATABLE / DO NOT BACK UP

    /var/lib/docker
    /var/lib/containerd
    Docker images
    container writable layers
    build/cache state
    package caches
    downloaded Pi-hole list cache
    Matrix PostgreSQL database under current policy
    Matrix media under current policy
    other obvious caches/history not deliberately preserved

18. BACKUP PRIORITY MODEL
===============================================================================

P0 - irreplaceable identity / access / secrets:
    Matrix signing key
    Matrix deployment/configuration secrets
    Matrix registration shared secret
    WireGuard private configuration
    important SSH access material
    Cloudflare credentials required for service restoration
    backup-repository credentials

P1 - small useful mutable state:
    Uptime Kuma state
    selected Pi-hole configuration
    selected NetAlertX/Scrutiny/Dockge/The Lounge state
    other small application databases that are genuinely worth preserving

P2 - useful/reproducible configuration:
    /opt/stacks Compose configuration
    /etc/unbound
    custom systemd units/timers
    recovery inventory / manifests
    package/service manifests

P3 - intentionally regenerate/lose:
    Matrix PostgreSQL database
    Matrix media store
    Matrix history/account/room state
    /var/lib/docker
    /var/lib/containerd
    images/layers/cache
    downloaded caches
    package caches
    expendable history data

19. RESTORE ORDER
===============================================================================

Suggested high-level rebuild order:

1. Reinstall Debian or a compatible successor.
2. Restore administrator / SSH access.
3. Restore network configuration.
4. Restore WireGuard identity/configuration.
5. Restore UFW/network policy.
6. Install Docker / Docker Compose.
7. Restore Compose/configuration files.
8. Restore Pi-hole and Unbound configuration.
9. Restore custom systemd units/timers.
10. Restore Cloudflare Tunnel configuration/credentials.
11. Recreate PostgreSQL as a new empty Matrix database.
12. Restore Matrix P0 files:
        compose.yaml
        .env
        homeserver.yaml
        log config
        kgivler.com.signing.key
        registration_shared_secret
13. Start the fresh Matrix deployment.
14. Verify matrix.kgivler.com client/federation APIs.
15. Verify kgivler.com Matrix .well-known delegation.
16. Recreate local Matrix users/services as needed.
17. Rejoin/rebuild room memberships/state as needed.
18. Restore selected Uptime Kuma / NetAlertX / Scrutiny / Dockge / The Lounge
    state.
19. Validate Pi-hole -> Unbound DNS flow.
20. Enable and test scheduled backup jobs.
21. Perform a representative encrypted peer restore.
22. Perform a representative offsite-object-storage restore.

22. SUMMARY
===============================================================================

Molasses is an old but currently healthy Dell Inspiron 3847 home server running
Debian 13 on a 1 TB mechanical HDD.

Its current responsibilities include:
    - Pi-hole
    - Unbound
    - Matrix Synapse + PostgreSQL
    - Cloudflare Tunnel
    - WireGuard
    - Uptime Kuma
    - NetAlertX
    - Scrutiny
    - The Lounge
    - PairDrop
    - Dockge
    - Dozzle agent
    - Beszel agent

The mechanical HDD is not itself the problem; allowing it to hold the only copy
of irreplaceable identity/configuration material would be.

The intended backup model is:

    tiny irreplaceable identity/secrets
        -> encrypted peer copy + independent encrypted offsite copy

    small useful application state
        -> preserve selectively where worthwhile

    Matrix PostgreSQL + media
        -> intentionally NOT backed up under the current minimal-recovery policy

    reproducible configuration
        -> Git where appropriate + cheap encrypted backup where useful

    Docker/runtime/cache data
        -> recreate instead

For Matrix specifically, the backup objective is to retain the kgivler.com
homeserver identity and configuration, not to preserve historical Matrix state.
