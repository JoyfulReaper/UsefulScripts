MOLASSES
========
Infrastructure / Recovery / Service Overview
Snapshot date: 2026-09-22

PURPOSE
-------
Molasses is Kyle's always-on home Debian server. It currently acts as a local
network utility host, DNS resolver/filter, Docker application host, observability
agent, IRC/web utility host, and Matrix homeserver.

This file is intended to answer:
- What is Molasses?
- What runs here?
- What starts it?
- Where is its configuration?
- Where is persistent data?
- Which secrets and identities are irreplaceable?
- What network does it participate in?
- What should be backed up?
- What can be recreated?
- What would be needed to rebuild it?
- What have we NOT inventoried yet?

It is deliberately broader than a backup manifest.

16. BACKUP ARCHITECTURE / POLICY
===============================================================================

Molasses backup design is intentionally split by data type.

The VPSes should NOT become bulk storage for Molasses databases or Matrix media.

A. TINY IRREPLACEABLE / IDENTITY / ACCESS MATERIAL

    Examples:
        Matrix signing key
        Matrix database credentials / .env
        WireGuard private configuration
        important SSH/access material as appropriate
        other service identity keys or small secrets

    Policy:
        - include automatically when it is sensible and safe
        - preserve in the main backup
        - additionally keep a tiny encrypted/off-site peer copy on another VPS
          where appropriate

    Rationale:
        These files are tiny, extremely important, and have negligible storage
        impact.

B. MUTABLE DATABASE / APPLICATION DATA

    Examples:
        Matrix PostgreSQL logical dump
        Uptime Kuma state
        Scrutiny data if worth retaining
        NetAlertX state if worth retaining
        useful Pi-hole state
        selected Dockge/The Lounge data

    Destination:
        object storage / bucket

    Policy:
        Do NOT dump these into Clanker or ScopeCreep as the primary destination.

C. LARGE OR POTENTIALLY GROWING DATA

    Examples:
        Matrix local user media
        larger application databases/history

    Destination:
        object storage if preservation is desired

    Policy:
        apply explicit retention rather than allowing unbounded growth

D. REPRODUCIBLE CONFIGURATION

    Examples:
        compose.yaml files
        selected systemd units/timers
        Unbound configuration
        non-secret service configuration
        public infrastructure documentation

    Policy:
        Keep in Git where appropriate.
        Small configuration may also be included automatically in the main
        backup because the cost is negligible.

E. REGENERATABLE / DO NOT BACK UP

    /var/lib/docker
    /var/lib/containerd
    Docker images
    container writable layers
    Docker build/cache state
    package caches
    downloaded Pi-hole list cache
    recreatable remote Matrix media/cache
    other obvious caches

===============================================================================
17. BACKUP PRIORITY MODEL
===============================================================================

P0 - irreplaceable identity / access / secrets:
    Matrix signing key
    Matrix .env / database credentials
    WireGuard private configuration
    important SSH access material
    Cloudflare credentials if required to restore service

P1 - important mutable application state:
    PostgreSQL logical dump
    selected Matrix local media
    Uptime Kuma state
    selected Pi-hole state
    other application databases worth preserving

P2 - useful configuration / convenience:
    /opt/stacks
    /opt/dockge configuration
    /etc/unbound
    selected /etc/pihole configuration
    custom systemd units/timers
    recovery inventory / manifests

P3 - regenerate instead:
    /var/lib/docker
    /var/lib/containerd
    images/layers/cache
    downloaded lists/caches
    package caches
    expendable query/history data if not intentionally retained

18. MATRIX BACKUP NOTES
===============================================================================

The Matrix PostgreSQL database is critical to the homeserver, but critical does
NOT mean it should be copied to another small VPS.

Preferred design:

    Molasses live PostgreSQL
            |
            | pg_dump + compression
            v
       object storage

Separate tiny identity backup:

    kgivler.com.signing.key
    Matrix .env / important credentials
            |
            | encrypted tiny copy
            v
    Clanker and/or ScopeCreep

Matrix media:
    Local user-uploaded media should be backed up to object storage if preserving
    it matters.

    Remote/recreatable media cache should not consume backup capacity merely
    because it exists locally.

The mechanical HDD is not itself the problem; allowing it to hold the only copy
of irreplaceable data would be.

The intended backup model is:

    tiny irreplaceable identity/secrets
        -> main backup + encrypted tiny peer copy where sensible

    databases / mutable application state
        -> object storage

    large/growing preserved data
        -> object storage with explicit retention

    reproducible configuration
        -> Git and/or included cheaply in backup

    Docker/runtime/cache data
        -> recreate instead

The next infrastructure task is NOT to keep adding services. It is to choose the
object-storage destination, implement a Molasses backup around this documented
policy, and test that a restore is actually possible.
