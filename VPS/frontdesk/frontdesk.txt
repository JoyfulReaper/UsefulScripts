FRONTDESK
=========
Production / Storage VPS Inventory and Recovery Notes
Initial commissioning: 2026-09-30
Updated through FrontDesk backup-storage and recovery audit on 2026-10-02.

PURPOSE
-------
FrontDesk is the intentionally boring production/storage VPS.

Primary roles:
- stable Linux production host for selected services;
- approximately 1 TB of bulk storage for archives, downloads, backups and staging;
- private management through the existing WireGuard network;
- Mission Control fleet node;
- possible future clearnet web/application host.

Current policy:
- keep DN42/Yggdrasil/tcpnoise/random routing experiments off this host unless its role is deliberately changed;
- do not add a nested client VM just because /dev/kvm exists;
- prefer simple service/container isolation for future workloads;
- do not treat FrontDesk's own 1 TB disk as independent disaster recovery for FrontDesk itself.

This file contains operational information, not secrets.

Important limitation:
    FrontDesk's 1 TB storage is in the same VPS/provider account as FrontDesk.
    Data existing only there is NOT independent disaster recovery.

FrontDesk itself does not currently have a documented independent configuration
backup. A rebuild should not require preserving the bulk repository files on the
OS disk, but the following small recovery material deserves an independent,
secure copy or reproducible recovery procedure:
    /etc/restic-rest-server/users.htpasswd
    /etc/wireguard/
    SSH authorized-key/access configuration
    UFW policy
    /etc/fstab
    systemd/service configuration
    backup-molasses authorized_keys restrictions
    Mission Control/Beszel configuration and secret material as appropriate

Do not put secret-bearing copies of those files in Git.

The restic CLI was not installed on FrontDesk during the 2026-10-02 audit.
That is not required for its current rest-server role because repository
maintenance is initiated by the clients. Install restic locally only if a
specific FrontDesk-side recovery/verification workflow needs it.

No recent storage I/O/ext4 errors were found in the audit, and systemd reported
zero failed units.

A future tertiary copy of selected recent FrontDesk backups to Molasses has been
recorded as an idea. It must remain non-authoritative: never move/delete the
FrontDesk source as part of that copy job, and do not make primary backup success
depend on the old Molasses HDD.

17. RECOVERY ORDER
===============================================================================

If FrontDesk is unreachable:

1. Test private management:
       ping 10.99.0.14
       ssh frontdesk

2. Test through the FreeBSD jump box / ProxyJump.

3. Check Clanker's wg0 peer state for FrontDesk.

4. Use GreenCloud/VirtFusion provider console/VNC if WireGuard is unavailable.

5. On the provider console inspect:
       ip -br addr
       ip route
       ip -6 route
       systemctl status wg-quick@wg0
       wg show wg0
       ufw status verbose
       systemctl status ssh
       systemctl status missioncontrol-agent
       systemctl status beszel-agent
       systemctl --failed

6. Do not leave public SSH enabled merely for convenience after recovery.
