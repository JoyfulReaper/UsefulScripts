MOLASSES
========
Infrastructure / Recovery / Service Overview
Snapshot date: 2026-09-25

PURPOSE
-------
Molasses is Kyle's always-on home Debian server. It currently acts as a local
network utility host, DNS resolver/filter, Docker application host, monitoring
host, IRC/web utility host, Matrix homeserver, backup client, and DN42 client
routed through Clanker over WireGuard.

This file is intended to answer:
- What is Molasses?
- What runs here?
- What starts it?
- Where is its configuration?
- Where is persistent data?
- Which secrets and identities are irreplaceable?
- What is actually backed up?
- What is intentionally NOT backed up?
- What would be needed to rebuild it after a drive failure?
- How does Molasses reach DN42 and resolve DN42 DNS?

It is deliberately broader than a backup manifest.

The Matrix backup policy is intentionally conservative. Matrix is NOT treated
as a full-state archival service. The recovery goal is to retain the minimum
identity/configuration required to rebuild the same homeserver identity after a
disk failure, not to preserve PostgreSQL history, room/event history, or media.

9. MATRIX MINIMAL DISASTER-RECOVERY POLICY
===============================================================================

Matrix is intentionally NOT receiving a full backup.

Recovery goal:
    Rebuild a fresh Synapse instance using the same kgivler.com server identity
    and configuration.

Recovery goal is NOT:
    Restore every user, room membership, event, message, token, database row,
    thumbnail, upload, or cached remote media.

Included identity/configuration set:
    /opt/stacks/matrix/compose.yaml
    /opt/stacks/matrix/.env
    /opt/stacks/matrix/synapse/homeserver.yaml
    /opt/stacks/matrix/synapse/kgivler.com.log.config
    /opt/stacks/matrix/synapse/kgivler.com.signing.key
    /opt/stacks/matrix/synapse/registration_shared_secret

External configuration also required:
    - Cloudflare tunnel configuration/credentials for matrix.kgivler.com
    - kgivler.com .well-known Matrix delegation

Explicit Matrix exclusions:
    /opt/stacks/matrix/postgres/
    PostgreSQL logical dumps
    /opt/stacks/matrix/synapse/media_store/
    thumbnails
    remote media cache
    local uploaded media
    Matrix message/event history
    room state/history
    access-token/session state
    user/account database state

This is an intentional identity/configuration recovery policy, not a complete
Matrix state restore.

    Listener:
        127.0.0.1:5335 TCP/UDP

    Configuration:
        /etc/unbound

    DN42 configuration:
        /etc/unbound/unbound.conf.d/dn42.conf

Current DNS flow:
    LAN / WireGuard clients
        -> Pi-hole / pihole-FTL :53
        -> Unbound 127.0.0.1:5335
        -> normal recursive DNS and, for DN42 zones, DN42 anycast resolvers

DN42 forward DNS:
    dn42.

DN42 IPv4 reverse DNS:
    20.172.in-addr.arpa.
    21.172.in-addr.arpa.
    22.172.in-addr.arpa.
    23.172.in-addr.arpa.

DN42 IPv6 reverse DNS:
    d.f.ip6.arpa.

DN42 recursive anycast resolvers:
    172.20.0.53
    172.23.0.53
    fd42:d42:d42:54::1
    fd42:d42:d42:53::1

Unbound behavior:
    DN42 zones are marked domain-insecure because DN42 is outside the normal
    public DNSSEC hierarchy.

    dn42. is marked private-domain because valid DN42 answers can contain
    RFC1918/ULA addresses.

    DN42 IPv4 reverse zones and d.f.ip6.arpa. use:
        local-zone: "...zone..." nodefault

    This overrides Unbound's normal private empty-zone handling so those PTR
    requests can be forwarded to DN42 DNS.

Pi-hole behavior:
    dns.bogusPriv = false

    Verified 2026-09-25.

    This is intentional. Pi-hole's private-reverse NXDOMAIN behavior must be
    disabled so unknown private PTR lookups can reach Unbound and the DN42
    reverse forwarders.

Verified 2026-09-25:
    dn42. SOA:
        resolves through Unbound and through the Pi-hole -> Unbound path

    20.172.in-addr.arpa. SOA:
        resolves through the DN42 resolver path

    d.f.ip6.arpa. SOA:
        resolves through the DN42 resolver path

    PTR query for:
        172.20.220.49

    reaches DN42 DNS and currently returns authoritative DN42 NXDOMAIN because
    no PTR is published for that address.

    PTR query for:
        fdf0:e12c:5528::1

    likewise reaches DN42 DNS and currently returns authoritative DN42 NXDOMAIN.

Important ULA reverse note:
    d.f.ip6.arpa. represents fd00::/8 and therefore also includes local ULA
    space such as:
        fd42:42:42::/64

    If local PTR records are wanted for the private WireGuard ULA range, define
    a more-specific local reverse zone for that range so it wins over the broad
    DN42 d.f.ip6.arpa. forward.

Current dn42.conf shape:
    one server: block
    forward-zone for dn42.
    four IPv4 reverse forward-zones
    one d.f.ip6.arpa. forward-zone
    all using the four DN42 anycast resolver addresses above

18. BACKUP ARCHITECTURE / POLICY
===============================================================================

Molasses backup is IMPLEMENTED.

Backup script source in UsefulScripts:
    VPS/Backup/Molasses/backup.sh

Installed execution path expected by systemd:
    /usr/local/sbin/vps-backup

Staging:
    /var/lib/vps-backup/staging

Lock:
    /run/lock/vps-backup.lock

Backup destinations:

1. Peer backup on Clanker
    Repository:
        rest:http://10.99.0.1:8000/molasses/

    Tags:
        molasses
        peer

2. Independent Backblaze B2 repository
    Repository:
        s3:https://s3.us-east-005.backblazeb2.com/kgivler-backup-molasses

    Tags:
        molasses
        offsite
        b2

Notifications:
    ntfy endpoint:
        http://10.99.0.1:5197/vps-backups

    Success and failure notifications are emitted when credentials are available.

Backup prerequisites / secret files:
    /etc/vps-backup/peer.env
    /etc/vps-backup/peer-repository-password
    /etc/vps-backup/b2.env
    /etc/vps-backup/ntfy.env

Do NOT commit the contents of those secret files.

Backup process:
    - verify Clanker restic repository connectivity
    - verify B2 restic repository connectivity
    - build a fresh staging tree
    - stage /etc except backup credentials and Pi-hole history/cache
    - stage /opt/stacks with intentional Matrix/Scrutiny bulk exclusions
    - stage additional application/configuration paths
    - replace live SQLite copies with consistent SQLite .backup snapshots
    - run PRAGMA quick_check on each SQLite snapshot
    - generate a recovery manifest
    - send the same staged recovery set to Clanker
    - send the same staged recovery set to Backblaze B2
    - list recent snapshots
    - notify success/failure

The backup intentionally requires BOTH repositories to be reachable before the
normal run proceeds.

20. BACKUP MAINTENANCE
===============================================================================

Backblaze B2 maintenance script:
    VPS/Backup/Molasses/b2-repo-maintenance.sh

Installed execution path expected by systemd:
    /usr/local/sbin/b2-backup-maintenance

Schedule:
    Sunday 08:45
    randomized delay up to 15 minutes
    persistent timer

Operations:
    restic cat config
    restic unlock
    restic forget --keep-within 30d --prune
    restic check
    restic stats --mode raw-data

The same backup lock is used so repository maintenance cannot overlap the normal
backup run.

Current retention policy encoded in the script:
    keep all snapshots within 30 days

NOTE:
    Current script/repository configuration is documented here.

25. SUMMARY
===============================================================================

Molasses is an always-on Debian 13 home server on older Dell hardware with a
large local HDD.

Its current responsibilities include:
    - Pi-hole
    - Unbound
    - DN42 forward DNS
    - DN42 IPv4/IPv6 reverse DNS
    - DN42 client connectivity through Clanker
    - Matrix Synapse + PostgreSQL
    - Cloudflare Tunnel
    - WireGuard
    - Uptime Kuma
    - NetAlertX
    - Scrutiny
    - The Lounge
    - PairDrop
    - Dockge
    - Dozzle agent
    - Beszel agent
    - automated encrypted backup to Clanker
    - automated encrypted offsite backup to Backblaze B2

Important recent changes:
    - Molasses now has dedicated DN42 client addresses:
          172.20.220.59
          fdf0:e12c:5528::59

    - DN42 routes are provided by Clanker over wg0.

    - Docker networks were moved away from DN42's 172.20.0.0/14 space into
      192.168.63.0/24 through 192.168.70.0/24.

    - Pi-hole + Unbound now resolve .dn42 and DN42 reverse DNS.

    - Pi-hole dns.bogusPriv is intentionally false so DN42 PTR lookups can reach
      Unbound.

    - Molasses backups are implemented to both Clanker and Backblaze B2.

The mechanical HDD is not itself the problem; allowing it to hold the only copy
of irreplaceable identity/configuration material would be.

The current recovery model is:
    tiny irreplaceable identity/secrets
        -> encrypted peer copy + independent encrypted offsite copy

    small useful application state
        -> consistent snapshots/selective preservation

    Matrix PostgreSQL + media
        -> intentionally NOT backed up under the current minimal-recovery policy

    reproducible configuration
        -> Git where appropriate + encrypted backup

    Docker/runtime/cache data
        -> recreate

For Matrix specifically, the backup objective is to retain the kgivler.com
homeserver identity and deployment configuration, not historical Matrix state.
