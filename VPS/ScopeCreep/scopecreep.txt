Infrastructure / Recovery / Service Overview
Snapshot date: 2026-09-23

PURPOSE
-------
ScopeCreep is Kyle's secondary always-on Debian VPS. It currently acts as a
backup peer/storage host, monitoring-agent host, Docker utility host, WireGuard
node, and secondary infrastructure box.

This file is intended to answer:
- What is ScopeCreep?
- What runs here?
- What starts it?
- Where is persistent data?
- What backup responsibilities does it have?
- Which secrets/configuration matter for recovery?
- What network does it participate in?
- What would be needed to rebuild it?
- What have we NOT inventoried yet?

It is deliberately broader than a backup manifest.

10. SCOPECREEP BACKUP ARCHITECTURE
===============================================================================

ScopeCreep backs itself up to Clanker over the WireGuard network using restic.

Destination:
    rest:http://10.99.0.1:8000/scopecreep/

Restic snapshot metadata:
    host: scopecreep
    tags:
        scopecreep
        peer

Backup staging root:
    /var/lib/vps-backup/staging

The script:
    - requires root
    - prevents overlapping runs with flock
    - validates peer repository connectivity
    - stages a recovery tree
    - creates a recovery manifest
    - snapshots SQLite safely
    - sends the staged tree to Clanker using restic
    - sends success/failure notification through ntfy
    - removes staging data on exit

ntfy endpoint:
    http://10.99.0.1:5197/vps-backups

23. SUMMARY
===============================================================================

ScopeCreep is currently a small, clean secondary VPS with a narrow set of
responsibilities:

    - peer backup storage for Clanker
    - self-backup to Clanker
    - Mission Control Agent
    - Dockge
    - Dozzle agent
    - Beszel agent
    - Cloudflare Tunnel
    - WireGuard connectivity

Its critical state is small.

Mission Control now treats ScopeCreep as its own stable node. The Agent is
host-managed by systemd, exposes its API over the WireGuard network, collects
host/Docker state, and successfully publishes into the central Gateway on
Clanker. Its /etc/missioncontrol-agent.env file must actually be loaded by the
systemd EnvironmentFile drop-in; having the file on disk alone is not enough.

The biggest recovery concern is not disk volume; it is preserving the secret
files under /etc/vps-backup out-of-band, because ScopeCreep intentionally
excludes those credentials from its own peer backup.

The main remaining cleanup items are:
    - remove the disabled legacy Beszel deployment after a short soak period
    - remove its obsolete paths from the ScopeCreep backup script
    - document cloudflared safely
    - decide whether the reproducible Mission Control Agent binaries need backup
    - avoid DN42/Docker address overlap if DN42 is ever enabled here
