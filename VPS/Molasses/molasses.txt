MOLASSES
========
Infrastructure / Recovery / Service Overview
Snapshot date: 2026-09-27
Updated through hbg1 KVM/libvirt deployment, routed residential IPv6, the
three-router DN42 core, and the Molasses/FrontDesk backup migration and restore
verification on 2026-10-02.

PURPOSE
-------
Molasses is Kyle's always-on home Debian server. It acts as a local network
utility host, DNS resolver/filter, Docker application host, monitoring host,
IRC/web utility host, Matrix homeserver, backup client, KVM/libvirt host for
hbg1, and a DN42 client routed through Clanker over WireGuard.

Molasses is not a DN42 BGP router. It is an attached DN42 client/service host
with its own addresses from AS4242420425's allocation.

This file is intended to answer:
- What is Molasses?
- What runs here?
- What starts it?
- Where is its configuration?
- Where is persistent data?
- Which secrets and identities are irreplaceable?
- What is actually backed up?
- What is intentionally not backed up?
- What would be needed to rebuild it after a drive failure?
- How does Molasses reach DN42 and resolve DN42 DNS?

The Matrix backup policy remains intentionally conservative. The recovery goal
is to preserve homeserver identity/configuration rather than full historical
Matrix state.

creates consistent SQLite snapshots, generates a recovery manifest, and sends
the same staged recovery set to both Clanker and FrontDesk.

    - Pi-hole

    - DN42 reverse-DNS forwarding
    - DN42 client connectivity through Clanker
    - direct testing of ns1 and ns2

    - encrypted peer backup to Clanker
    - encrypted bulk-storage backup to FrontDesk
    - direct hbg1 VM backup to FrontDesk

DN42-specific current state:
    - Molasses uses dedicated .59 / ::59 client identities.
    - Clanker supplies routing.
    - Both Clanker ns1 and ScopeCreep ns2 are directly reachable from Molasses
      over IPv4 and IPv6.
    - Direct authoritative PTR queries now succeed for Clanker's router identity.
    - Ordinary recursive PTR discovery is still waiting on registry reverse
      delegation to become visible.

The current recovery model remains:
    irreplaceable identity/secrets
        -> encrypted Clanker + FrontDesk copies where included
        -> repository credentials independently preserved out-of-band

    small useful application state
        -> consistent selective snapshots

    Matrix historical state
        -> intentionally not preserved under current minimal-recovery policy

    reproducible configuration
        -> Git where appropriate + encrypted backup

    Docker/runtime/cache
        -> recreate
